# Define Feature Spec

把 `web` 功能的模糊需求整理成可供設計、前端與 Sanity 共用的功能規格。

## 開始前

1. 閱讀根目錄與目標目錄的 `AGENTS.md`。
2. 閱讀 `web/PRODUCT.md`、`web/DESIGN.md`、相關 `docs/specs/`、現有頁面與 Sanity schema。
3. 分開記錄已確認事實、示範內容、合理假設與待決事項；不得把現有假資料當成正式內容。

## 產出

建立或更新 `docs/specs/<feature>.md`，內容至少包含：

- 狀態：新規格從 `draft` 開始。
- 目標與受眾：使用者來到此功能的情境、要理解或完成的主要事情。
- 範圍與非目標：第一版涵蓋什麼，以及明確不處理什麼。
- 內容契約：欄位名稱、語意、型別、必填性、合理長度、最少／典型／最多數量、編輯責任與預定資料來源。
- 狀態與行為：一般、loading、empty、error、缺少選填內容、長內容及互動回饋。
- 響應式、鍵盤操作、語意結構與替代文字要求。
- 可觀察且可測試的驗收條件。
- 待決事項、依賴及下一階段所需輸入。

內容模型描述「內容是什麼」，不要用目前版面位置替欄位命名。若一項待決事項會改變資料關係、主要操作或頁面範圍，先向使用者確認；其他細節以明確假設繼續。

## 完成門檻

檢查規格和 `PRODUCT.md`、既有行為沒有衝突，連結及路徑有效。規格仍可保留非關鍵待決事項，但必須足以讓設計階段不需要自行發明產品需求。此 Skill 不修改 UI、schema 或正式資料。
